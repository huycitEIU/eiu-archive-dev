# ADR 003

# Using Layered Architecture (MVC-inspired) for Backend API

- Status: Accepted
- Date: 2026-07-30

## Context

The project is a document storage and sharing system that provides RESTful APIs for user authentication, document management, file storage, sharing, and access control.

As the system grows, the backend is expected to support additional features such as document versioning, file search, notifications, and audit logging. To ensure maintainability and scalability, the codebase should clearly separate business logic from request handling and data access.

The architecture should:

- Promote separation of concerns.
- Improve code readability and maintainability.
- Simplify testing and debugging.
- Support future feature expansion.
- Allow independent modification of business logic and data access.
- Provide a consistent structure for all API endpoints.

The alternatives considered were:

- Layered Architecture (MVC-inspired)
- Traditional MVC
- Clean Architecture
- Hexagonal (Ports and Adapters) Architecture

## Decision

We will adopt a **Layered Architecture**, which is a backend-oriented variation of the MVC (Model-View-Controller) pattern.

The backend will be organized into the following layers:

- **Controller** – Handles HTTP requests and responses, validates input, and delegates work to the service layer.
- **Service** – Implements business logic such as document sharing, permission checking, and file management.
- **Repository (Data Access Layer)** – Interacts with the database and Cloudflare R2 for data persistence.
- **Model** – Represents the application's data entities and database schema.

Each layer has a single responsibility and communicates only with adjacent layers. Controllers do not access the database directly, and business rules are centralized in the service layer.

The request flow is:

```
Client
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database / Cloudflare R2
```

## Consequences

### Positive

- Clear separation between presentation, business logic, and data access.
- Improved maintainability through modular and organized code.
- Easier unit testing, as each layer can be tested independently.
- Business logic is reusable across multiple API endpoints.
- Database or storage implementations can be modified with minimal impact on higher layers.
- New developers can understand the project structure more quickly.

### Negative

- More files and boilerplate compared to a simpler architecture.
- Requests pass through multiple layers, introducing a small amount of additional complexity.
- For small features, creating separate controller, service, and repository classes may feel repetitive.

### Risks

- If responsibilities between layers are not enforced, business logic may leak into controllers or repositories.
- Overusing the service layer can result in large, difficult-to-maintain service classes.
- Future architectural changes (e.g., migration to Clean Architecture) may require refactoring, although the layered approach provides a solid foundation for such evolution.
