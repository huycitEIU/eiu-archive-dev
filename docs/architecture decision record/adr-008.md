# ADR 008

# Using JWT for Authentication

- Status: Accepted
- Date: 2026-07-30

## Context

The document storage and sharing system requires a secure authentication mechanism to identify users and protect resources such as documents, folders, and sharing permissions.

The authentication solution should:

- Support stateless authentication.
- Scale easily across multiple application instances.
- Be compatible with RESTful APIs.
- Minimize server-side session management.
- Be widely adopted and well supported.

The alternatives considered were:

- JSON Web Token (JWT)
- Session-based Authentication
- OAuth 2.0
- API Keys

## Decision

We will use **JSON Web Tokens (JWT)** for user authentication.

After a successful login, the server issues a signed JWT containing the user's identity and authorization information. The client stores the token securely and includes it in the `Authorization` header using the Bearer scheme for subsequent requests.

Protected API endpoints validate the JWT before processing requests.

## Consequences

### Positive

- Stateless authentication improves scalability.
- No server-side session storage is required.
- Easy integration with RESTful APIs.
- Widely supported across frontend and backend frameworks.
- Suitable for distributed systems and future microservices.

### Negative

- Token revocation is more difficult than invalidating server-side sessions.
- Expired tokens require refresh or re-authentication.
- Tokens must be stored securely on the client.

### Risks

- Improper JWT validation may lead to security vulnerabilities.
- Long-lived tokens increase the impact of token leakage.
- Weak signing secrets may compromise authentication security.
