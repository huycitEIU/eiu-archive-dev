# ADR 009

# Using RESTful API Design

- Status: Accepted
- Date: 2026-07-30

## Context

The backend exposes APIs for user management, document storage, folder organization, and document sharing.

A consistent API design is required to improve maintainability, interoperability, and ease of integration with the React frontend and potential third-party clients.

The API design should:

- Follow widely accepted standards.
- Be resource-oriented.
- Use standard HTTP methods and status codes.
- Support future expansion without breaking existing clients.
- Be easy to understand and document.

The alternatives considered were:

- RESTful API
- GraphQL
- RPC-style API

## Decision

We will design the backend using **RESTful API principles**.

The API will:

- Represent resources using meaningful URLs.
- Use standard HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`).
- Return appropriate HTTP status codes.
- Exchange data using JSON.
- Protect secured endpoints using JWT authentication.
- Maintain stateless communication between client and server.

Example endpoints:

```
GET    /api/documents
GET    /api/documents/{id}
POST   /api/documents
PUT    /api/documents/{id}
DELETE /api/documents/{id}

POST   /api/auth/login
POST   /api/auth/register
```

## Consequences

### Positive

- Consistent and predictable API structure.
- Easy integration with React frontend.
- Broad compatibility with HTTP clients and developer tools.
- Simplifies API documentation and testing.
- Supports future client applications such as mobile apps.

### Negative

- Complex resource relationships may require multiple API calls.
- REST may be less flexible than GraphQL for highly customized queries.

### Risks

- Inconsistent endpoint naming can reduce API usability.
- Poor versioning strategy may introduce breaking changes for clients.
- Improper use of HTTP methods or status codes may violate REST principles.
